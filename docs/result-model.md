# 验证计划与结果模型

当前实现是应用内部的数据契约与汇总逻辑，既不读取 OFD，也不执行密码、证书或时间戳校验。构造的结果是否真实可信，由未来的业务验证器负责。

## 组成

| 类型 | 用途 |
| --- | --- |
| `CheckSpec` | 声明对象 ID、检查 ID、名称和是否必需 |
| `CheckResult` | 记录实际状态、原因、字段位置、期望值、实际值、标准依据、人工建议和字符串上下文 |
| `VerificationReport` | 关联检查计划与实际结果，给出整体状态、状态统计和缺项清单 |

同一报告中以 `(object_id, check_id)` 唯一定位检查，例如 `("signature-1", "certificate_chain")`。多个签章可以使用相同检查 ID，但必须使用不同对象 ID。

输入列表会转为元组，结果上下文会复制为只读映射，避免调用者事后修改原始列表或字典而悄悄改变报告。

## 状态与汇总

单项状态：`passed`、`failed`、`indeterminate`、`skipped`、`error`、`not_applicable`。整体状态：`passed`、`failed`、`incomplete`。

按以下顺序汇总：

1. 任意实际结果失败（包括可选项）时，整体失败；其他已收集的结果和缺项仍保留。
2. 没有计划，或任意计划项尚无结果时，整体不完整。
3. 必需且适用的检查存在无法确定、跳过或错误时，整体不完整。
4. 必需且适用的检查至少有一项，并且全部通过时，整体通过。
5. 全部不适用或仅有可选项时，整体不完整。

已执行的可选项若为无法确定、跳过或错误，不会覆盖必需项全部通过的整体结论，但明细和统计中仍包含这些问题。调用方必须一并展示明细，不应只展示汇总状态。

`not_applicable` 和 `skipped` 等状态也必须提供非空原因。模型只检查原因存在，不验证标准适用性；使用者不能通过随意标记“不适用”来宣称满足标准。

## 使用示例

先按 [README](../README.md) 安装项目，然后运行 [合成示例](../examples/result_report.py)：

```powershell
.\.venv\Scripts\python.exe examples/result_report.py
```

示例人为构造三项结果，未读取或验证真实文件：

| 检查 | 状态 |
| --- | --- |
| 签名值 | `passed`（人为构造） |
| 证书链 | `indeterminate`（演示缺少材料） |
| 时间戳 | `not_applicable`（仅本合成场景的演示策略） |

整体输出为 `incomplete`，JSON 同时包含 `planned_checks`、`checks`、`missing_checks` 和 `summary`。

## 输出与时间含义

- `to_dict()` 返回普通字典；`to_json()` 使用 UTF-8 友好的中文字符串，不强制转换为 Unicode 转义序列。
- JSON `schema_version` 当前为 `1.0`。后续字段兼容变更需同步文档和测试。
- `generated_at` 是报告生成时间，默认使用 UTC，并要求传入的自定义时间带时区。它不是签章时间、证书有效性基准或可信时间戳。
- `source_name` 是调用者提供的输入标识，不代表输入文件已经被打开或其内容已经受保护。
- 可选上下文字段为字符串，模型不自动脱敏；调用方负责选择必要内容并去除敏感数据。

## 无效输入与边界

- 重复计划、重复结果、计划外结果、空 ID 或空原因会被拒绝。
- 无效状态、错误的字段类型和不支持的上下文值会被拒绝，不会静默转成成功结果。
- 模型不会自动执行遗漏检查或捕获验证器的业务异常；后续调度器需要把单项异常转换为 `error`，继续独立检查，再生成报告。
- 模型只能发现已声明计划中的缺项，不能推断是否已声明某标准要求的全部检查。完整的标准条款映射留待业务实现。
